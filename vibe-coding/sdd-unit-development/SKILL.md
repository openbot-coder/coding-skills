# SDD — 规范驱动单元开发

## 核心思想

> **先写规范，再写实现，最后统一测试。**

SDD（Specification-Driven Development）与 TDD 的核心区别：

| 方面 | TDD（旧） | SDD（新） |
|------|-----------|-----------|
| 顺序 | 测试 → 代码 → 重构 | **规范 → 代码 → 测试** |
| 粒度 | 逐个功能点循环 | 整任务规范先行 |
| 测试时机 | 每个功能点先写测试 | **所有任务实现后统一写测试** |
| 关注点 | 测试驱动设计 | 规范驱动设计 |

## 开发流程

```
┌────────────────────────────────────────────────────────────┐
│             步骤一：逐个任务实现（SDD 模式）                  │
│                                                            │
│  1. 规范（Spec） → 定义接口签名、行为约定、边界条件          │
│  2. 实现（Implement） → 按规范编写生产代码                   │
│  3. 标记完成（Done） → 暂存，继续下一个任务                  │
└────────────────────────────────────────────────────────────┘
                            ↓
┌────────────────────────────────────────────────────────────┐
│          步骤二：统一单元测试（所有任务完成后）               │
│                                                            │
│  1. 遍历所有任务的规范，编写测试用例                         │
│  2. 覆盖正例 + 反例 + 边界值                                │
│  3. 目标：单元测试覆盖率 100%                                │
│  4. 未覆盖行标注 # UNCOVERED: [原因]                        │
└────────────────────────────────────────────────────────────┘
```

## 步骤一：逐个任务实现

### 第 1 步：写规范（Spec）

为每个功能点定义接口规范，包括：

**函数/方法签名：**
```python
def calculate_discount(price: float, coupon_code: str | None, user_level: int) -> float:
    """计算最终折扣价格
    Args:
        price: 原价（> 0）
        coupon_code: 优惠券代码（可选，None 表示无优惠券）
        user_level: 用户等级（1-5）
    Returns:
        折扣后价格（> 0）
    Raises:
        ValueError: 当 price <= 0 或 user_level 不在 1-5 范围
    """
    ...
```

**行为约定：**
| 场景 | 输入 | 预期行为 |
|------|------|----------|
| 无优惠券 | price=100, coupon=None, level=3 | 按等级折扣，返回 90 |
| 有效优惠券 | price=100, coupon="SAVE20", level=1 | 优惠券叠加等级折扣，返回 72 |
| 无效优惠券 | price=100, coupon="INVALID", level=1 | 忽略无效券，仅等级折扣 |
| 价格为 0 | price=0, ... | 抛出 ValueError |

**边界条件：**
- 最小/最大值（如 price 最小值 0.01，最大值 999999）
- 空值/None 处理
- 特殊输入（如空字符串、负数）

### 第 2 步：实现（Implement）

严格按照规范编写生产代码：

```python
def calculate_discount(price: float, coupon_code: str | None, user_level: int) -> float:
    if price <= 0 or not (1 <= user_level <= 5):
        raise ValueError("invalid price or user level")

    level_discount = {1: 0.1, 2: 0.15, 3: 0.2, 4: 0.25, 5: 0.3}
    discount = level_discount[user_level]

    if coupon_code == "SAVE20":
        discount += 0.2  # 叠加优惠券折扣

    return round(price * (1 - discount), 2)
```

**实现原则：**
- **只实现规范中定义的内容** — 不要 YAGNI（You Ain't Gonna Need It）
- **不要写测试** — 测试将在步骤二统一添加
- **保持代码清晰** — 命名、结构符合规范

### 第 3 步：标记完成

```bash
python scripts/execute.py --name <变更名称> --task <编号> --action done
```

暂存代码，继续下一个任务。

## 步骤二：统一单元测试

### 时机

**所有任务都标记为完成后**，统一编写单元测试。

### 测试三个维度

#### 正例 — 验证预期行为

- 正常输入 → 正常输出
- 典型使用场景 → 功能正确完成
- 验证"它能做我们说它能做的事"

#### 反例 — 验证错误处理

- 无效输入 → 正确的错误响应
- 缺少必要参数 → 明确的错误信息
- 无权限访问 → 401/403 而非 500
- 验证"它不能做我们说它不能做的事"

#### 边界值 — 验证临界行为

- 最小值、最大值、零值、空值
- 刚好等于阈值 vs 刚好超过阈值
- 并发/竞争条件（如果适用）

### 覆盖率要求：100%

每一行未覆盖的代码必须以行内注释标注无法覆盖的原因：

```python
# UNCOVERED: 防御性代码 — 此 NotImplementedError 仅在子类未实现时触发，
# 但所有子类均已实现，此行为路径不可达
raise NotImplementedError
```

**可接受的未覆盖原因：**
- 防御性代码（如抽象基类的 `NotImplementedError`）
- 框架架构限制（如流式生成器中的异常无法被外层 try/except 捕获）
- 第三方库内部路径
- 竞争条件中理论上可能但实践中不可复现的路径

**不可接受的未覆盖原因：**
- "太难测试"
- "太简单不需要"
- "之后补"
- "这个分支永远不会执行"

如果一行代码真的永远不执行，那它就不应该存在。删掉它。

## 验证检查清单

在步骤二完成（即单元测试通过）之后：

- [ ] 每个新函数/方法都有测试
- [ ] 所有测试通过
- [ ] 输出干净（无错误、警告）
- [ ] 测试使用真实代码（除非不可避免否则不用 mock）
- [ ] **每个功能点覆盖正例 + 反例 + 边界值**
- [ ] **单元测试覆盖率 100%，未覆盖行已标注原因**
- [ ] 测试结果已记录到 progress.md

## 规范 vs 测试 关系图

```
规范（Spec）                   测试（Test）
────────                      ──────────
定义接口                     验证接口
描述行为                     验证行为
声明边界                     验证边界
设计时的产物                 验证时的产物

规范驱动实现                 测试验证实现
```

## 常见问题

| 问题 | 答案 |
|------|------|
| 规范写多细？ | 够实现即可，接口签名 + 行为约定 + 边界条件 |
| 实现时遇到规范未覆盖的情况？ | 更新规范再实现，保证规范永远是准确的 |
| 所有任务实现后才写测试，会不会漏测？ | 不会，按规范编写测试，覆盖所有已定义的场景 |
| 测试发现 bug 怎么处理？ | 修复实现代码，确保测试通过。先修复再继续写其他测试 |
| 如果实现与规范不一致？ | 以规范为准修改实现，或者规范不合理则先更新规范 |
