# Task Breakdown

> Phase 1（部分）→ AI 自驱动：接收需求文档，输出任务列表 + 优先级

## 何时使用

- 用户已批准需求文档（`design.md` 中 `✅ 已批准`）
- 需要将功能需求拆解为可执行的技术任务

## 前置检查

1. 读取 `design.md`，确认需求定义完整
2. 读取 `progress.md`，确认当前阶段
3. 读取 `ANTI-PATTERNS.md`，避免常见拆分错误

## 执行流程

### Step 1：解析需求

从 `design.md` 提取：

- **目标**：用户故事 / 功能描述
- **范围**：包含哪些子模块
- **约束**：技术限制、性能要求、兼容性

### Step 2：生成任务列表

输出格式（写入 `progress.md`）：

```markdown
## 任务清单

| # | 任务 | 类型 | 优先级 | 依赖 | 预估时间 |
|---|------|------|--------|------|----------|
| 1 | 初始化项目骨架 | setup | P0 | - | 15min |
| 2 | 实现核心数据模型 | feature | P0 | T1 | 30min |
| 3 | 实现 API 接口 | feature | P0 | T2 | 45min |
| 4 | 编写单元测试 | test | P1 | T3 | 30min |
| 5 | 集成测试 | test | P1 | T4 | 30min |
| 6 | 文档更新 | docs | P2 | T5 | 15min |

## 任务详情

### T1: 初始化项目骨架
- **类型**: setup
- **描述**: 创建目录结构、配置文件、基础模块
- **交付物**: 目录结构、pyproject.toml / package.json
- **验收标准**: 项目可正常运行 `pytest` / `go build`
```

### Step 3：生成架构方案

```markdown
## 架构方案

### 模块划分
- `src/` — 生产代码
- `tests/` — 测试代码
- `docs/` — 文档

### 依赖关系
```
config → models → services → api
                    ↓
              repositories
```

### 技术选型
- 语言：Python 3.10+
- 测试：pytest
- Linter：ruff
```

### Step 4：更新 progress.md

- 在 `## 阶段状态` 中标记 `任务拆解: 🔄 进行中`
- 完成后标记 `任务拆解: ✅ 已完成`

## 任务类型

| 类型 | 说明 | 示例 |
|------|------|------|
| `setup` | 项目初始化 | 创建目录、配置、依赖 |
| `feature` | 功能实现 | 实现某个功能模块 |
| `refactor` | 重构 | 优化现有代码 |
| `test` | 测试编写 | 单元测试、集成测试 |
| `docs` | 文档编写 | 更新 README、API 文档 |
| `fix` | 缺陷修复 | BUG 修复 |

## 优先级定义

| 优先级 | 说明 | 策略 |
|--------|------|------|
| P0 | 核心功能 | 必须先做，无替代方案 |
| P1 | 重要功能 | P0 完成后做 |
| P2 | 辅助功能 | P1 完成后做 |

## 反模式

- ❌ 按"前端/后端"拆分（应按业务领域）
- ❌ 任务粒度过细（每个函数一个任务）
- ❌ 忽略依赖关系
- ❌ 没有验收标准

## 触发条件

当 `design.md` 中存在：

```markdown
## 审批状态
| 阶段 | 状态 | 审批人 | 时间 |
|------|------|--------|------|
| 需求定义 | ✅ 已批准 | 宝爷 | 2026-05-23 |
```

且 `progress.md` 中 `任务拆解` 状态为 `⬜ 待执行` 时，自动执行本技能。

## 输出要求

1. 将任务清单写入 `progress.md`
2. 将架构方案写入 `progress.md`
3. 更新 `progress.md` 中的阶段状态
4. 如需 Git，提交：`chore: 任务拆解完成`
