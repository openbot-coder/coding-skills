# Debugging & Verification

> Phase 3 → AI 自驱动：测试失败 → 分析诊断 → 修复 → 重测循环

## 何时使用

- SDD 开发阶段完成，所有任务 `✅ 已完成`
- 进入集成测试阶段
- 单元测试或集成测试出现失败

## 前置检查

1. 确认 `progress.md` 中所有任务均为 `✅ 已完成`
2. 运行 `pytest -v --tb=long` 获取完整测试报告
3. 记录失败测试详情

## 执行流程

### 调试循环

```
测试失败
   ↓
分析失败原因（根因诊断）
   ↓
制定修复方案
   ↓
实施修复
   ↓
重新运行测试
   ↓
┌── 通过？──→ 下一个测试
│  否
└── 回到分析
```

### Step 1：全量测试

```bash
pytest -v --tb=long --no-header 2>&1 | tail -50
```

### Step 2：根因诊断

对每个失败测试，做 5W 分析：

| 维度 | 问题 | 答案 |
|------|------|------|
| What | 测试什么场景？ | 测试空输入处理 |
| Where | 哪个断言失败？ | `assert func([]) is None` |
| When | 什么条件下触发的？ | 当输入为空列表时 |
| Why | 为什么失败？ | 函数返回 `0` 而非 `None` |
| How | 如何修复？ | 增加 `if not input: return None` |

### Step 3：记录调试信息

在 `progress.md` 中记录：

```markdown
## 调试记录

| 时间 | 问题 | 根因 | 修复 | 状态 |
|------|------|------|------|------|
| 14:30 | 测试T1边界值失败 | 未处理空输入 | 增加空值判断 | ✅ 已修复 |
```

### Step 4：修复代码

1. 最小化修改（只改一处）
2. 修改后立即运行该测试
3. 确认通过后运行全部测试

### Step 5：回归验证

```bash
pytest -v --tb=short 2>&1 | tail -20
```

确保：
- 全部测试通过 ✅
- 覆盖率不下降 ✅
- 新代码无 Warning ✅

## 修复效率原则

| 情况 | 策略 |
|------|------|
| 单个断言逻辑错误 | 直接修复 |
| 接口改变 | 更新规范 → 代码 → 测试 |
| 复杂错误 | 写诊断代码 → 分段验证 |
| 环境问题 | 检查依赖/配置/路径 |
| 多次重试失败 | 记录问题，请求人类介入 |

## 反模式

- ❌ 不找根因只改表面
- ❌ 一次改多处以图侥幸
- ❌ 修复后不跑全量测试
- ❌ 覆盖率下降忽略
- ❌ 跳过集成测试直接验收

## 触发条件

当 `progress.md` 中 `所有任务均已完成` 且 `集成测试` 状态为 `⬜ 待执行` 时自动执行。
