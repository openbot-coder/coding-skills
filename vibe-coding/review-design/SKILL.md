# Review Design

> Phase 0（部分）→ AI 自审 + 人工审批：检查需求文档完整性，提交人工审批

## 何时使用

- 用户提交了需求描述
- 需要在进入开发前审查设计文档

## 核心原则

**人工审批点**：需求文档必须经过人工审批后才能进入开发阶段。AI 只负责自审和辅助。

## 执行流程

### Step 1：读取 design.md

读取 `docs/vibe-coding/design.md`，检查各部分是否完整：

### Step 2：AI 自审清单

对以下每一项给出判断（✅/⚠️/❌）：

| 检查项 | 说明 |
|--------|------|
| 背景清晰 | 有明确的业务背景和动机 |
| 目标明确 | 有具体、可衡量的目标 |
| 范围界定 | 有明确的包含/不包含边界 |
| 成功标准 | 有可验证的验收标准 |
| 用户故事 | 有用户视角的描述 |
| 技术可行 | 在当前技术栈下可实现 |

### Step 3：自审报告

```markdown
## 自审报告

### 完整性检查

| 检查项 | 状态 | 备注 |
|--------|------|------|
| 背景清晰 | ✅ | 业务场景描述清楚 |
| 目标明确 | ✅ | 3个目标具体可衡量 |
| 范围界定 | ⚠️ | "不包含"部分需要补充 |
| 成功标准 | ✅ | 5个标准可验证 |
| 用户故事 | ⚠️ | 缺少验收条件 |
| 技术可行 | ✅ | 技术选型合理 |

### 问题清单

1. ⚠️ 范围界定中"不包含"部分需要补充具体内容
2. ⚠️ 用户故事缺少验收条件（Given-When-Then）

### 建议

- 补充"不包含"的具体边界
- 为每个用户故事补充验收条件
- 增加性能指标（响应时间、并发数等）

### 自审结论

✅ 自审通过，可提交人工审批
⚠️ 自审通过但有改进建议
❌ 自审未通过，需要补充内容
```

### Step 4：提交人工审批

更新 `design.md` 中的审批状态：

```markdown
## 审批状态

| 阶段 | 状态 | 审批人 | 时间 | 备注 |
|------|------|--------|------|------|
| 需求定义 | ⏳ 待审批 | - | - | 自审通过，提交审批 |
| 设计审查 | ⬜ 待执行 | - | - | - |
| 最终验收 | ⬜ 待执行 | - | - | - |
```

### Step 5：向用户展示

向用户展示：

1. **自审报告**：AI 检查结果
2. **设计摘要**：核心内容摘要
3. **待确认项**：需要用户决策的问题
4. **审批请求**：`design.md` 是否可以批准进入开发？

---

## 人工审批流程

### 用户操作

用户在 `design.md` 中更新审批状态：

```markdown
## 审批状态

| 阶段 | 状态 | 审批人 | 时间 | 备注 |
|------|------|--------|------|------|
| 需求定义 | ✅ 已批准 | 宝爷 | 2026-05-23 | 可以开始 |
| 设计审查 | ⏳ 待审批 | - | - | - |
| 最终验收 | ⬜ 待执行 | - | - | - |
```

### AI 响应

- ✅ 已批准 → 自动进入下一阶段（任务拆解）
- ❌ 未通过 → 等待用户修改后重新提交

---

## 设计审查（阶段 2）

需求批准后，进行设计审查：

```markdown
## 设计审查

### 架构审查

| 检查项 | 状态 | 说明 |
|--------|------|------|
| 模块划分合理 | ✅ | 按业务领域划分 |
| 依赖关系清晰 | ✅ | 无循环依赖 |
| 接口设计合理 | ⚠️ | API 命名需统一 |

### 技术风险

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 第三方依赖版本 | 中 | 固定版本号 |
| 并发性能 | 高 | 预建缓存 |

### 审查结论

✅ 审查通过，可开始任务拆解
⚠️ 需补充技术方案
❌ 需重新设计
```

---

## 反模式

- ❌ AI 直接跳过审批进入开发
- ❌ 审批状态不更新
- ❌ 问题不记录、不反馈
- ❌ 不向用户展示设计内容

## 触发条件

当用户提交需求文档后自动执行。
