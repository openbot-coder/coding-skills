# 五阶段工作流指南

## 概述

vibe-coding 采用五阶段工作流，确保开发过程的规范化和可追溯性。

```
阶段1: 需求分析 → 阶段2: 任务拆解 → 阶段3: 代码执行 → 阶段4: 测试验证 → 阶段5: 需求归档
```

## 阶段1：需求分析

**时机：** 需求出现，需要设计

**目标：** 明确目标、背景、成功标准和范围

### 子流程

#### writing-design（需求调研）

**功能：**
- 探索项目上下文，理解真正的问题
- 通过提问澄清需求、约束和成功标准
- 提出 2-3 种方案并分析权衡
- 将需求要点和设计方案记录到 `{name}-design.md`

**操作：**
1. 运行 `python scripts/design.py --name <变更名称> --desc "<简要描述>"`
2. 完成需求调研，记录到 `{name}-design.md`
3. 设计文档草稿完成后，进入 review-design

#### review-design（设计审查）

**审查内容：**
- 目标是否清晰、可验证
- 背景是否充分
- 成功标准是否可测试
- 范围边界是否明确
- 假设和风险是否已识别
- 安全风险和影响范围

**审查流程：**
1. 读取 `docs/vibe-coding/changes/{name}/{name}-design.md`
2. 检查完整性：目标、背景、成功标准、范围
3. 检查质量：假设、风险、可验证性、安全、影响范围
4. 输出审查报告：指出问题或确认通过
5. 发现问题 → 返回 writing-design 修改 → 重新审查
6. 审查通过 → 请求用户批准

#### 用户批准

**批准后操作：**
1. 更新 `{name}-design.md` 中的"设计状态"表
2. 执行 Git 提交：`git add {name}-design.md && git commit -m "feat: {name} 设计已获批准"`
3. 进入阶段2（任务拆解）

## 阶段2：任务拆解

**时机：** 设计已获用户批准

**目标：** 将设计文档拆解为可执行的任务清单

**操作：**
1. 运行 `python scripts/plans.py --name <变更名称>`
2. 在 `{name}-progress.md` 中填充阶段2的计划概述：
   - 架构方案
   - 实施步骤
   - 依赖关系
   - 风险评估
3. 在 `{name}-progress.md` 中填充任务清单（每个任务 10~20 个功能点）
4. 确认计划和任务清单完整后，进入阶段3

**规则：**
- 每个任务必须是可独立验证的
- 任务粒度：每个任务 10~20 个功能点
- 任务之间标注依赖关系
- plans 和 tasks 内容整合到 `{name}-progress.md` 中

## 阶段3：代码执行

**时机：** 计划已定，任务需要实施

**目标：** 按任务清单执行编码

### TDD 模式

**TDD 铁律：** 没有失败的测试就不能写生产代码

**红-绿-重构循环：**
```
红（写失败测试）→ 绿（最少代码通过）→ 重构（清理）→ 下一个
```

**测试三维度覆盖：**
- **正例**：正常输入 → 正常输出
- **反例**：无效输入 → 正确错误响应
- **边界值**：最小值、零值、空值、最大值

**覆盖率要求：**
- 单元测试覆盖率目标：100%
- 未覆盖行必须以 `# UNCOVERED: [原因]` 标注原因
- 仅需单元测试，无需集成测试

### 操作流程

1. 运行 `python scripts/execute.py --name <变更名称> --action list` 查看任务
2. 开始任务：`python scripts/execute.py --name <变更名称> --task <编号> --action start`
3. 编码前：使用 ripgrep 了解现有代码结构
4. 编码中：遵循 TDD，每完成一个小功能点后做防跑偏检查
5. 编码后：记录发现到 `{name}-progress.md`
6. 完成任务：`python scripts/execute.py --name <变更名称> --task <编号> --action done`
7. 跳过任务：`python scripts/execute.py --name <变更名称> --task <编号> --action skip`
8. 所有任务完成后，进入阶段4

## 阶段4：测试验证

**时机：** 编码完成，需要验证结果

**目标：** 验证实现是否满足设计要求

**操作：**
1. 运行 `python scripts/verify.py --name <变更名称> --action start` 开始验证
2. 进行系统集成测试：验证所有模块协同工作
3. 发现问题 → 进入调试流程 → 修复 → 重新测试
4. 验证通过后，运行 `python scripts/verify.py --name <变更名称> --action done`
5. 更新 `{name}-progress.md` 中的验证结果
6. 提交用户批准：向用户展示验证结果，请求批准
7. 批准后进入阶段5（需求归档）

**系统集成测试要点：**
- 模块间接口调用是否正确
- 数据流转是否完整
- 端到端功能是否正常
- 异常情况处理是否一致

**验证通过标准：**
- 测试用例充分、完整
- 单元测试覆盖率 100%
- 无法覆盖的代码需用户批准
- 集成测试通过

## 阶段5：需求归档

**时机：** 阶段4测试验证已通过，且用户已批准

**前提条件：**
- ✅ 阶段4验证通过
- ✅ 用户批准（必须）
- ✅ 当前在 `develop` 分支

**操作：**
1. 运行 `python scripts/archive.py --name <变更名称>`
2. 脚本将：
   - 提交 Git 到 `develop` 分支
   - 推送到远程仓库
   - 询问是否打标签（如需打标签，创建 `v<version>/<name>` 格式的标签）
   - 将变更目录移动到 `docs/vibe-coding/changes/archive/`
   - 创建 PR 将 `develop` 分支合并到 `main` 分支

**归档条件：**
- ✅ 阶段4验证通过（测试充分、覆盖率100%、集成测试通过）
- ✅ Git 已提交到 `develop`
- ✅ `{name}-progress.md` 中阶段5状态已更新

## 状态判断

| 文件状态 | 当前阶段 | 下一步 |
|----------|----------|--------|
| `{name}-design.md` 不存在 | 阶段1：writing-design | 开始需求调研 |
| `{name}-design.md` 存在，设计状态"Agent审查"为 ⏳ | 阶段1：review-design | 审查设计 |
| `{name}-design.md` 审查通过，"用户批准"为 ⏳ | 阶段1：等待批准 | 请求用户批准 |
| `{name}-design.md` 已批准 | 阶段2：任务拆解 | 运行 plans.py |
| 阶段2完成，有未完成任务 | 阶段3：代码执行 | 运行 execute.py |
| 所有任务完成 | 阶段4：测试验证 | 运行 verify.py |
| 验证通过，"用户批准"为 ⏳ | 阶段4：等待批准 | 请求用户批准 |
| 用户已批准 | 阶段5：需求归档 | 运行 archive.py |

## 快速决策表

| 你听到... | 阶段 | 操作 |
|-----------|------|------|
| "我想做 X" / "添加功能" / "实现 XX" | 阶段1 | writing-design |
| "设计写好了，帮我看看" | 阶段1（子流程） | review-design |
| "设计审查通过了" | 阶段1（子流程） | 请求用户批准 |
| "设计批准了" | 阶段2 | 任务拆解 |
| "计划做好了，开始做" / "执行任务 N" | 阶段3 | 代码执行 |
| "做完了" / "应该没问题了" | 阶段4 | 测试验证 |
| "验证通过了" | 阶段4（等待批准） | 请求用户批准 |
| "批准了" / "没问题，可以收尾" | 阶段5 | 需求归档 |
